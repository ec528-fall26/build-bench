# g2 root-cause report (13 Nov 2026). All builds: arm64 docker (native), `dpkg-buildpackage -B -us -uc`, build deps from the .dsc via mk-build-deps, today's archive.

Note: the drawterm case id is `launchpad-resolute-amd64-arm64-drawterm-dc4b454175ea` (not b8dff3c0528a). It has no rc9c repair.diff.

## 1. rapmap (launchpad-resolute-amd64-arm64-rapmap-7cdd6f2b0223)
1. reproduces today: yes (ubuntu:resolute arm64, same two undefined references).
2. root cause: `src/KSW2Aligner.cpp` (lines ~223/227 and ~358/362) calls `ksw_extz2_sse41` / `ksw_extz2_sse2` unconditionally in `if (haveSSE41) ... else if (haveSSE2) ... else ksw_extz(...)`. Those symbols are defined only in `ksw2_extz2_sse.c` under `#ifdef __SSE4_1__` / `#elif defined(__SSE2__)`. On aarch64 neither macro exists (simde does not define them), so the `#else` branch defines `ksw_extz2_sse` instead, and `ksw2_dispatch.c` (which would map it) is not in the CMake source list (`src/CMakeLists.txt` lines 70-83) and is also guarded by KSW_CPU_DISPATCH, which only the x86 branch of CMakeLists sets. Log: `KSW2Aligner.cpp:227: undefined reference to ksw_extz2_sse2`, `:223 ... ksw_extz2_sse41`. At run time haveSSE41/haveSSE2 come from `x86_simd()` which returns 0 on non-x86 (`__cpuidex` sets cpuid[0]=0), so those branches are dead on arm64; only the link references are the problem.
3. what our agent's edit did: rc5 log: `ksw2_extz2_sse.c:13:6 error: old-style parameter declarations` (compile error in the .c). rc9c repair.diff: pasted wrapper definitions between the `#if/#elif/#else` function header and its `{` body (so the header is no longer followed by the body; it parses wrongly), plus defined the wrappers a second time unconditionally, and changed the .cpp else-branch to call `ksw_extz2_sse` with a different argument list. The preprocessor chain was split from the function body.
4. fix (smallest: make the dead x86-only branches not exist off x86):
```
--- a/src/ksw2pp/KSW2Aligner.cpp
+++ b/src/ksw2pp/KSW2Aligner.cpp
@@ -219,6 +219,7 @@   (operator() for EXTENSION, std::vector overload)
   int z = config_.dropoff;
+#if defined(__x86_64__) || defined(__i386__)
   if (haveSSE41) {
     ksw_extz2_sse41(...);
   } else if (haveSSE2) {
     ksw_extz2_sse2(...);
-  } else {
+  } else
+#endif
+  {
     ksw_extz(...);
   }
@@ -354,6 +357,7 @@   (same change in the raw-pointer overload)
```
(both `if (haveSSE41)` blocks, i.e. 2 places, +3/-1 lines each; as a `debian/patches` entry or direct edit). verified: PASS (ubuntu:resolute arm64: link succeeded, ctest 2/2 passed, packages built). Caveat: the verifying build was incremental on a tree whose objects had been compiled with identical flags in the preceding failing build (only the .cpp changed and relinked); the failing build had compiled everything else fine.
5. what an agent without build feedback needed: (a) the log gives the exact caller lines (`KSW2Aligner.cpp:223/227`); open that file and see the calls are plain function calls inside runtime-flag `if`s; (b) grep the definitions: `grep -n "ksw_extz2_sse" src/ksw2pp/*.c` shows names are chosen by `__SSE4_1__`/`__SSE2__`, which are not defined on aarch64 (simde does not define them), so the library exports `ksw_extz2_sse`, not the two names; (c) `grep -n "haveSSE\|x86_simd\|__cpuidex" src/ksw2pp/KSW2Aligner.cpp` shows `__cpuidex` returns 0 when not `__x86_64__/__i386__`, so the branches are provably dead; therefore guard the calls with the same `__x86_64__` macro the file already uses at lines 26/34. The tempting path (editing the macro ladder in the `.c`) leaves a function header that must stay directly attached to `{`; a hint "an edit that touches a function header must keep header and `{` adjacent, and run a syntax check (`gcc -fsyntax-only`) on any C file you edit" would have blocked both failed attempts. Also: do not add code that duplicates a symbol that dispatch would define.
6. class: x86-only code (SSE variants referenced unconditionally; only x86 build sets the macros that name them).

## 2. libmbim (launchpad-jammy-amd64-arm64-libmbim-32c606c4686e)
1. reproduces today: yes, but only when built the way the original log was. ubuntu:22.04 arm64 with only `build-essential`+Build-Depends (no Build-Depends-Indep) and `dpkg-buildpackage -B`: fails identically at `dh_autoreconf` (`Can't exec "gtkdocize"`). With gtk-doc-tools + libglib2.0-doc installed and `dpkg-buildpackage -b` the UNMODIFIED source builds and all tests pass (rc=0).
2. root cause: yes, the arch-indep build-dependency difference. dsc: `Build-Depends-Indep: gtk-doc-tools <!nodoc>, libglib2.0-doc <!nodoc>`; the Launchpad arm64 log is `Build Type: any`, `dpkg-buildpackage ... -B`, "Merged Build-Depends: debhelper-compat (= 13), pkg-config, autoconf-archive, gobject-introspection, help2man, libgirepository1.0-dev, libglib2.0-dev" (log lines 560-561; no gtk-doc-tools). `debian/rules binary-arch` -> `dh_autoreconf -a` -> autoreconf runs `gtkdocize` because `configure.ac:134 GTK_DOC_CHECK(1.0)` -> `Can't exec "gtkdocize"` (log 1125). amd64 passed because amd64 builds are full (`-b`/with indep) so gtk-doc-tools is installed.
   KEY FACT for the benchmark: the organizer's validator build is NOT `-B`. rc5 log shows `debian/rules binary` (not `binary-arch`) and `I: Retrieving gtk-doc-tools 1.33.2-1` (rc5 log line 688): the validator installs Build-Depends-Indep and builds everything. So for this case the original source would very likely pass validation untouched; the failing target log is not what the validator reproduces.
3. what our agent's edit did: rc9c repair.diff comments out `GTK_DOC_CHECK(1.0)` in configure.ac (`dnl`). With gtk-doc-tools now installed in the validator, this made automake fail: `gtk-doc.make:25: error: GTK_DOC_USE_LIBTOOL does not appear in AM_CONDITIONAL` (and BUILD_HTML, BUILD_PDF, ENABLE_GTK_DOC, HAVE_GTK_DOC): `docs/reference/libmbim-glib/Makefile.am:82` includes `gtk-doc.make`, which needs the conditionals GTK_DOC_CHECK defines. The edit broke a build that worked.
4. fix (only matters for a true `-B` build; harmless for `-b`): skip autoreconf in arch-only builds, the shipped `configure` is in the orig tarball:
```
--- a/debian/rules
+++ b/debian/rules
@@ -4,7 +4,7 @@
 export DEB_BUILD_MAINT_OPTIONS = hardening=+all
 
 %:
-	dh $@ --with gir
+	dh $@ --with gir$(if $(filter binary-arch build-arch,$(MAKECMDGOALS)), --without autoreconf)
```
verified: PASS in ubuntu:22.04 arm64 with gtk-doc-tools NOT installed, `dpkg-buildpackage -B`, tests all PASS (test-common, uuid, cid, message, fragment, message-parser, message-builder, proxy-helpers). Also PASS unmodified with `-b` + gtk-doc-tools. (Inference: an unchanged submission passes the validator.) Note `dh_listpackages` cannot be used to detect `-B` here: it lists all packages, so the existing `ifeq ($(filter libmbim-glib-doc,$(shell dh_listpackages)),)` in rules is always false; my first attempt using it did not skip autoreconf. MAKECMDGOALS (`binary-arch` under -B) works.
5. what an agent without build feedback needed: read the Build Type/command in the log (`-B`, "Build Type: any") and the dsc `Build-Depends-Indep`; realise the missing tool (`gtkdocize`) belongs to an indep dep so an `-B` build cannot have it; then either (a) conclude the validator, which installs indep deps, needs no change (a hint "check whether the failing tool's package is only in Build-Depends-Indep; the validator environment may differ from the log") or (b) not touch autoconf macros (removing GTK_DOC_CHECK breaks `gtk-doc.make` in docs/ Makefile.am). Never edit configure.ac macros that other Makefile.am files depend on without grepping for their conditionals.
6. class: packaging step (arch-indep vs arch-dep build-dependency, `-B` vs `-b`).

## 3. obs-time-source (launchpad-noble-amd64-arm64-obs-time-source-04ee01f2e706)
1. reproduces today: yes at the compile step per the rc5 log and original log (same error); I did not rebuild unmodified, but confirmed the cause directly in an ubuntu:24.04 arm64 container (`pkg-config --cflags libobs` prints the literal generator expressions).
2. root cause: `/usr/lib/aarch64-linux-gnu/pkgconfig/libobs.pc` from `libobs-dev` has `Cflags: -I${includedir} -DHAVE_OBSCONFIG_H -DSIMDE_ENABLE_OPENMP $<$<AND:$<COMPILE_LANGUAGE:C>,$<BOOL:C_COMPILER_SUPPORTS_OPENMP_SIMD>>:-fopenmp-simd> $<$<AND:$<COMPILE_LANGUAGE:CXX>,...>:-fopenmp-simd>` (a packaging bug: CMake generator expressions leaked into the installed .pc). Meson passes them to `cc`: `cc: error: $<$<AND:$<COMPILE_LANGUAGE:C>,...>:-fopenmp-simd>: linker input file not found` (original log 1983-1986). (Inference: it is arm64-only because libobs adds the SIMDe/openmp-simd flags only on non-x86 targets, so the amd64 .pc lacks them.) The flag is not from this project at all; `meson.build` just has `dependency('libobs')`.
3. what our agent's edit did: rc5: no effective change (same error at ninja). rc9c: added `'openmp=disabled'` to `default_options` in meson.build; the project has no such option, and openmp is not what feeds the flag (the flag comes from libobs.pc), so meson setup errors on the unknown option / nothing changes.
4. fix (debian/rules; regenerate a cleaned .pc into the build tree and point pkg-config at it):
```
--- a/debian/rules
+++ b/debian/rules
@@ -2,6 +2,7 @@
 include /usr/share/dpkg/pkg-info.mk
+include /usr/share/dpkg/architecture.mk
@@ -12,6 +13,13 @@
 %:
 	dh $@
 
+override_dh_auto_configure:
+	mkdir -p debian/pkgconfig
+	sed 's/\$$<[^ ]*//g' /usr/lib/$(DEB_HOST_MULTIARCH)/pkgconfig/libobs.pc > debian/pkgconfig/libobs.pc
+	PKG_CONFIG_PATH=$(CURDIR)/debian/pkgconfig dh_auto_configure
+
 execute_before_dh_auto_configure:
```
verified: PASS (ubuntu:24.04 arm64, `dpkg-buildpackage -B -j2`, plugin `time-source.so` compiled, linked, packaged). The sed is a no-op where the .pc is clean (amd64). No new deps, no download.
5. what an agent without build feedback needed: the log's error string is the whole clue: the "file" named in the cc error is literally a CMake generator expression with `-fopenmp-simd` in it, and `time-source.c`/`meson.build` contain no such string. grep of the source tree finds nothing, so the text must come from an installed file; the only external inputs are `pkg-config` modules (libobs, pangocairo), and `cat /usr/lib/*/pkgconfig/libobs.pc` would show it. A hint like "when a compiler flag in the error is not in the tree, grep /usr/lib/*/pkgconfig and /usr/share for it" leads to the fix. Equivalent fix in meson.build: replace `dependency('libobs')` by `declare_dependency(dependencies: cc.find_library('obs'), compile_args: ['-I/usr/include/obs','-DHAVE_OBSCONFIG_H'])` (not built by me).
6. class: dependency API drift (installed `-dev` package metadata bug; arm-path only).

## 4. rust-generator (launchpad-jammy-amd64-arm64-rust-generator-c5207d2ba61d)
1. reproduces today: not rebuilt unmodified; the rc5 log and original log agree: `thread 'main' panicked at 'Unsupported architecture: aarch64-unknown-linux-gnu', build.rs:30:13`. My patched build passed through the build script, so the diagnosis is confirmed from the other side (ubuntu:22.04 arm64, rustc 1.75).
2. root cause: generator 0.6.20 ships a hand-written context-switch implementation for x86_64 only: `build.rs` match has the aarch64 arm commented out (`// "arm64" | "aarch64" => "arm64"`), `src/detail/asm/` contains only `asm_x86_64_*` files, `src/detail/mod.rs` and `src/stack/mod.rs` have `#[cfg(... target_arch = "x86_64")]` only. A real port is needed; the crate does not support aarch64 in this version (upstream added it in later versions).
3. what our agent's edit did: rc5: `error[E0432]: unresolved imports self::asm, crate::detail::initialize_call_frame, swap_registers, Registers` (log line 1631). rc9c repair: uncommented all arch arms in `build.rs` incl. arm/mips/ppc/i386, made the asm compile conditional on file existence (it does not exist for any of them), and added `#[cfg(x86_64)]` to the `pub use self::asm::...` line. So on aarch64 the Rust code has no `asm` module at all and no `swap_registers`; even if it had compiled the crate would have no working context switch (and `stack/mod.rs` has no `sys` for aarch64).
4. fix: a real port, about 75 lines of assembly/Rust in 2 new files and 3 one-line edits (smaller than it sounds because aarch64 AAPCS has a simple callee-saved set):
 - `build.rs`: uncomment `"arm64" | "aarch64" => "arm64",` (abi becomes `aapcs`, format `elf`, so the file expected is `src/detail/asm/asm_arm64_aapcs_elf_gas.S`).
 - `src/detail/mod.rs`: add `#[cfg(all(unix, target_arch = "aarch64"))] #[path = "aarch64_unix.rs"] pub mod asm;` before the `pub use self::asm::...` line.
 - `src/stack/mod.rs` line 11: `#[cfg(all(unix, any(target_arch = "x86_64", target_arch = "aarch64")))]`.
 - new `src/detail/asm/asm_arm64_aapcs_elf_gas.S`: `prefetch` = `prfm pldl2keep,[x0]; ret`; `swap_registers(out=x0,in=x1)` stores/loads x19-x28, x29, x30, sp (via x2) and d8-d15 with stp/ldp at offsets 0..160 then `ret`; `bootstrap_green_task` = `mov x0,x19; mov x1,x20; mov x30,xzr; br x21`.
 - new `src/detail/aarch64_unix.rs`: same `extern "C"` declarations as x86_64_unix.rs, `Registers { gpr: [usize; 22] }` (slots 0-9 x19-x28, 10 fp, 11 lr, 12 sp, 14-21 d8-d15), and `initialize_call_frame` setting x19=arg, x20=arg2, x21=fptr, fp=0, lr=bootstrap_green_task, sp=align_down(stack.end())-16.
 Full diff text is in `~/rootcause/g2/rg/rust.diff` on the instance (ignore its hunks for `.cargo-checksum.json`, `Cargo.lock`, `Cargo.toml.orig`: those are rewritten by the dh-cargo build, not by me). verified: PASS (ubuntu:22.04 arm64, `dpkg-buildpackage -B` without -j; real tests ran: lib unit tests 2 passed incl. `reg_context::test::test_swap_context`, integration tests 28 passed, 0 failed). Caveat: with `-j2` the debian cargo wrapper in my local run broke on make's "Entering directory" noise being parsed as the target triple (artefact of my local `-j`; the validator log showed the same noise but still reached the real error, so it is probably unaffected).
5. what an agent without build feedback needed: the panic message plus `ls src/detail/asm` (x86_64 files only) and the commented-out arch arms in build.rs tell it this is a missing port, not a switch to flip. The agent must then decide to write the assembly: it needs the facts that `Registers` is `#[repr(C)]` and shared by name between `swap_registers` (asm) and `initialize_call_frame`, and the AAPCS64 callee-saved set (x19-x28, x29, x30, sp, d8-d15). An agent that only uncomments arms (as rc9 did) cannot pass: any edit that does not create `asm` for aarch64 leaves `unresolved imports`. Hint that would help: "if the failing step is an architecture `match` that panics, check whether the per-arch implementation files exist in the tree; if not, a port (new files) is required and must also be wired into every `cfg(target_arch)` in the crate (grep `target_arch`)". The `grep -rn target_arch src` would have shown the third site (`stack/mod.rs`).
6. class: arm-only code missing (x86-only code in the crate; needs a port).

## 5. drawterm (launchpad-resolute-amd64-arm64-drawterm-dc4b454175ea)
1. reproduces today: not rebuilt unmodified (log 1565-1568 and rc5 are identical and unambiguous); fixed build PASS on ubuntu:resolute arm64.
2. root cause: `Make.unix:21-23`: `libmachdep.a:` target does `arch=\`uname -m|sed 's/i.86/386/;s/Power Macintosh/power/; s/x86_64/amd64/'\`; (cd posix-$$arch && make)`. On arm64 `uname -m` = `aarch64`, so it looks for `posix-aarch64`, which does not exist (tree has posix-386, posix-amd64, posix-arm (32-bit), posix-mips, posix-power, posix-sun4u). Log: `/bin/sh: 2: cd: can't cd to posix-aarch64`, `Make.unix:22: libmachdep.a Error 2`.
3. what our agent's edit did: rc5 log: no error lines surfaced in the file I inspected beyond the same make failure; no rc9c repair.diff exists for this case. Treat as "no effective change submitted" (inference).
4. fix: map `aarch64` to a new `posix-arm64` directory. `posix-arm`'s `tas.c` is 32-bit ARM (`ldrex`), which does not assemble on aarch64, so a new dir is needed. The other three files in posix-amd64/posix-arm are identical C (diff -q showed md5block.c, sha1block.c, getcallerpc.c identical across both), so copy them.
```
--- a/Make.unix
+++ b/Make.unix
@@ -22,2 +22,2 @@
-	arch=`uname -m|sed 's/i.86/386/;s/Power Macintosh/power/; s/x86_64/amd64/'`; \
+	arch=`uname -m|sed 's/i.86/386/;s/Power Macintosh/power/; s/x86_64/amd64/; s/aarch64/arm64/'`; \
 	(cd posix-$$arch &&  make)
```
plus new directory `posix-arm64/` = copy of `posix-amd64/{Makefile,getcallerpc.c,md5block.c,sha1block.c}` and new `posix-arm64/tas.c`:
```
#include "u.h"
#include "libc.h"

int
tas(long *x)
{
	int v;

	v = __atomic_exchange_n(x, 1, __ATOMIC_ACQUIRE);
	switch(v) {
	case 0:
	case 1:
		return v;
	default:
		print("canlock: corrupted 0x%lux\n", v);
		return 1;
	}
}
```
verified: PASS (ubuntu:resolute arm64, `dpkg-buildpackage -B -j2`, `drawterm` and `libmachdep.a` built, package produced; no test suite). Note `getcallerpc` copied from amd64 (`((uintptr*)a)[-1]`) is not the true return address on aarch64; it is only used as a malloc debugging tag (inference from grep: callers pass it to `setmalloctag`).
5. what an agent without build feedback needed: the log names the failing command and the missing directory (`cd: can't cd to posix-aarch64`) and `Make.unix:22`. `ls` of the tree shows the posix-<arch> dirs. It needs to notice (a) the `sed` mapping only covers x86 names, (b) the nearest dir `posix-arm` is 32-bit (read its `tas.c`: `ldrex/strex`), so mapping aarch64->arm would trade one failure for another, (c) the per-arch dir contains only 4 files of which one (tas) is arch-specific. Hint: "when the failing step is a per-architecture directory that is missing, diff the existing per-arch directories to see what is genuinely arch-specific before choosing the nearest one."
6. class: arm-only code missing (build system lacks an aarch64 port directory; small).

## Cross-case question: `-B` and "only in the full build"
Seen in 1 of 5 cases (libmbim): the original failure was a tool (`gtkdocize`) that is only in `Build-Depends-Indep`, because the Launchpad arm64 build is `dpkg-buildpackage -B`. In the other four (rapmap, drawterm, obs-time-source, rust-generator) the original logs are also `-B`/binary-arch but the failure is a real arm64 issue, not a missing indep dependency (4 of 5 ruled out by reproducing the fix on arm64 under `-B`). Important observation about the validator: rc5 logs for libmbim show `debian/rules binary` and gtk-doc-tools installed, so the organizer builds the full set, meaning an `-B`-only failure in the original log does not reproduce there. Sample is tiny (5); this says nothing about the rate across the 58.

## Agent-facing summary of checks that would have helped
- Syntax-check any C/C++ file the agent edits (rapmap: both failed attempts did not parse).
- For missing-tool failures: compare the log's `Build Type`/`-B` against `Build-Depends-Indep` and check which environment the validator uses.
- When an error string is not found in the tree, grep installed pkg-config files (obs-time-source).
- When the failing step is "unsupported architecture", list per-arch files; uncommenting arms without the implementation does not help (rust-generator).
- Per-arch directory selection: check that the nearest directory is the same word size (drawterm).
