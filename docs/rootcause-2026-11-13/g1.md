# Group g1 root-cause report (13 Nov 2026)

All builds: native arm64 containers on the instance, today's archive (not the frozen lock). Diffs and scratch trees are under `~/rootcause/g1/{xm,xq,le,xx,rf}/` (`xm/xm.diff`, `le/le.diff`, `rf/rf.diff`, `xx/edit-*.sh`, `xx/flow.sh`). Containers removed.

## 1. xmbmon, noble (`launchpad-noble-amd64-arm64-xmbmon-a78a68bcce2f`) and questing (`...-questing-...-ad2ecb4e1183`)

1. reproduces today: yes, ubuntu:24.04 arm64 (rc5 log shows the same). Questing: original log has the same errors (ubuntu:25.10 not rebuilt unmodified; the fix was built there).
2. root cause: `io_cpu.h` is x86-only by design (port I/O via `inb/outb` asm, `iopl()` from `<sys/io.h>`), and the Makefile hard-codes `-DLINUX` (debian/patches/makefile.patch makes `DEFS=... -DLINUX` unconditional; configure only sets `-DLINUX` for `i?86-*-linux`). Log: `io_cpu.h:5:10: fatal error: sys/io.h: No such file or directory` (noble log line 1770; questing log lines 1036-1062, many objects). glibc has no `<sys/io.h>` on aarch64. Beyond the include, `io_cpu.h` lines 40-80 contain six inline functions with `"inb %1,%0"`-style asm, which cannot assemble on arm64 (that is the `impossible constraint in 'asm'` error the agent hit after guarding only the include). `io_static.c` needs `SET_IOPL()` and `RESET_IOPL()` defined.
3. what our agent's edit did: rc5 log (`~/devval-rc5-logs/logs/<noble case>.txt`) ends at the unchanged `io_cpu.h:5: sys/io.h` error, so whatever rc5 submitted left the include in place. rc9c (noble) changed only line 4: `#ifdef LINUX` to `#if defined(LINUX) && (defined(__i386__) || defined(__x86_64__))`. That drops the `<sys/io.h>` branch, but the file then falls through to the FreeBSD `#else` (`SET_IOPL()` = `open("/dev/io")`, needs `<fcntl.h>`, `extern int iofl`) and still compiles the asm. Not built by us; the asm failure is certain from the unchanged asm block. Questing: rc5 says `Agent made no allowed input change`.
4. fix (whole fix is `io_cpu.h`; the same file content is in both releases, `cmp` identical after patches):

   verified: PASS. Noble: ubuntu:24.04 arm64, `dpkg-buildpackage -b` rc=0, both .debs built. Questing: ubuntu:25.10 arm64, same edit, rc=0, both .debs built. Package has no tests. The resulting binary can only report "no I/O permission" at run time, it cannot read hardware (inference: `OpenIO()` returns -1 via `SET_IOPL() < 0`).
   Why it is reasonable to build at all: it is not. The tool reads motherboard sensor chips through x86 I/O ports. Debian itself restricted it: 2.05-8 had `Architecture: amd64 hurd-i386 i386 kfreebsd-amd64 kfreebsd-i386 knetbsd-i386`; 2.05-9 (the Ubuntu version here, "Changed architecture to any") broadened it and broke on arm; Debian 2.05-12 (3 Sep 2025, closes #1112637) set `Architecture: i386 x32 amd64`. Test I ran: setting `Architecture: i386 x32 amd64` in debian/control on arm64 makes `dpkg-buildpackage -b` exit 0 with `dh: warning: No packages to build` and zero .debs (a validator that checks artifacts would probably fail it; inference). So the benchmark expects either the stub edit above or the case is effectively "upstream should not build here".
5. what an agent without build feedback needed: (a) the log names only `io_cpu.h:5` as the first error, but the error list in the questing log (and one `grep` for `asm` in `io_cpu.h`) shows the file is a block of x86 port-I/O asm below the include; the whole header must be treated as one unit, not just line 4-5. (b) `grep -n "IOPL\|my_in\|INb" *.c *.h` shows every user goes through `SET_IOPL/RESET_IOPL/INb/OUTb`, so the safe edit is to provide those names (with failing `SET_IOPL`) rather than remove them. (c) The Makefile forces `-DLINUX`, so guarding on `LINUX` alone is wrong; guard on `__x86_64__/__i386__`. A check that would have led there: "after editing, grep the same header for other x86-only constructs (`__asm__`, `<sys/io.h>`, `cpuid`) and make sure each is under the same guard"; the agent made the edit with no compile, so the only available check is reading the whole file once.
6. class: x86-only code.

## 2. libelas, resolute (`launchpad-resolute-amd64-arm64-libelas-8f3152c7b0d2`)

1. reproduces today: yes, ubuntu:26.04 arm64 (g++ 15.2). First error is the CMake one, as in the original log.
2. root cause: two layers. (i) `CMakeLists.txt:2 cmake_minimum_required (VERSION 2.6)` is rejected by CMake 4.x (`CMake Error at CMakeLists.txt:2`, original log line 1390). (ii) The library is hand-written SSE2 intrinsics: `src/elas.h:32`, `src/filter.h:25-26`, `src/descriptor.cpp:24` include `<emmintrin.h>`/`<pmmintrin.h>`; `src/filter.cpp` (about 150 uses of `__m128i`, `_mm_add_epi16`, `_mm_loadu_si128`, ...), `src/elas.cpp` (`_mm_sad_epu8`, `_mm_extract_epi16`, `_mm_set1_ps`, `_mm_load_ps`, ...) and `_mm_malloc/_mm_free` all need them. rc5 log first error after CMake: `filter.h:48:45: error: '__m128i' does not name a type`. The `-msse3` flag was already removed by Debian's `no-system-dependent-build-flags.patch`.
   No fallback path exists: there is no scalar variant and no `#ifdef __SSE2__` anywhere in the tree. simde and sse2neon are NOT available: the original log's package list (line 1270) has neither, `Build-Depends` is only `cmake, debhelper-compat`, and the tree ships neither. Debian has not fixed it either: Debian `20150630-2` only adds `compat-with-cmake4.patch`.
3. what our agent's edit did: rc5 fixed CMake (log shows the deprecation warning instead of the error) and then failed at `filter.h __m128i`, so it did not touch `filter.h`/`elas.h`. rc9c (`repair.diff`): bumps cmake version; in `descriptor.cpp` and `elas.cpp` replaces `_mm_malloc/_mm_free` with `malloc/free` and wraps an `#include <emmintrin.h>` with a stray `#endif` (no matching `#if`; syntax error) in `descriptor.cpp`; guards the includes in `filter.h`. That leaves all `__m128i`/`_mm_*` uses in `filter.cpp`/`elas.cpp`, so it cannot build (not built by us; this follows from the unchanged intrinsic code, inference, plus the unbalanced `#endif`).
4. fix: bump cmake version, and on non-x86 put a small NEON stand-in for the 25 intrinsics actually used on the include path ahead of the system headers. No new build dependency (`arm_neon.h` is part of GCC on aarch64). The two new headers are new files in `src/compat/` and no existing C++ file changes. Full text in `~/rootcause/g1/le/le.diff`.

Sanity run: `elas-demo` on `img/cones_left/right.pgm` completes and writes a non-trivial disparity map. I did not compare numerically against an x86 build (inference: semantics match because each intrinsic maps to its exact NEON counterpart; `_mm_max_ps` NaN behaviour may differ). Note `src/elas.cpp:1320` builds the abs mask with `_mm_set1_ps(0x7FFFFFFF)` (an upstream bug, a float not a bit mask); my `_mm_and_ps` is a bitwise AND, so behaviour is identical to x86.
   A "no SIMD" variant is not possible without rewriting `filter.cpp` and `elas.cpp` (about 300 lines of intrinsics).
5. what an agent without build feedback needed: (a) Count first: `grep -c "_mm_\|__m128" src/*` shows the intrinsics are in 4 files and are the core algorithm, so guarding includes (the rc9c route) can never compile. (b) Check for alternatives in the log: the package list has no simde/sse2neon, so the only dependency-free route is a local shim. (c) Because only a dozen distinct intrinsics are used (`grep -o "_mm_[a-z0-9_]*" | sort | uniq -c`), a shim header is a small bounded job. (d) Put it behind the CMake include path rather than editing six sources, so no existing file needs conditional edits. A hint that would help: "if more than N intrinsic call sites remain after a guard, write a compat header instead of guarding".
6. class: x86-only code (plus a CMake policy break that hides it).

## 3. libcrypt-xxhash-perl, plucky (`launchpad-plucky-amd64-arm64-libcrypt-xxhash-perl-9fa2d60e7af5`)

1. reproduces today: yes, ubuntu:25.04 arm64 with the realistic flow (see below): the same failure as rc5, including the `.pc` path.
2. root cause: `Build.PL` has `c_source => ['.', 'src']`. Module::Build's `process_support_files` (`/usr/share/perl5/Module/Build/Base.pm:2872-2892`) does `rscan_dir` on every listed directory and compiles every `*.c` found, so with `'.'` it compiles every C file in the whole tree: `ext/xxHash/xxhash.c` (needed, `xs/xxHash.xs` includes `xxhash.h` and needs its definitions) and `ext/xxHash/xxh_x86dispatch.c`. Nothing uses the dispatch file (`grep -rn dispatch xs lib src t` finds nothing; it only appears in MANIFEST). Original log: `ext/xxHash/xxh_x86dispatch.c:56:4: error: #error "Dispatching is currently only supported on x86 and x86_64."` plus `emmintrin.h: No such file`.
3. what our agent's edit did: the rc5 log shows the failing compile path is `./.pc/debian-changes-0.07-1build4/ext/xxHash/xxh_x86dispatch.c`: the agent edited `xxh_x86dispatch.c` in place (the validator turned it into patch `debian-changes-0.07-1build4`). The edited file compiles, but the pristine backup the quilt step stores under `.pc/` is again compiled by the recursive `'.'` glob and hits the same `#error`. No rc9c repair.diff exists for this case. I reproduced exactly this by guarding the file with `#if defined(__x86_64__)` and running my flow: build fails on `./.pc/debian-changes-0.07-1build4/ext/xxHash/xxh_x86dispatch.c:56` (variant `guard`).
4. fix: three variants, all verified with the realistic flow (apply edit in `dpkg-source -x` tree, `dpkg-source --auto-commit -b`, `dpkg-source -x` the new .dsc into a fresh dir so `.pc/` exists, `dpkg-buildpackage -b`): ubuntu:25.04 arm64.
   (A) debian/rules only (smallest, scoped to non-x86, no upstream file touched so `.pc/` gets nothing): PASS rc=0, `Result: PASS` (29 tests of `t/Crypt-xxHash.t` run and pass).

5. what an agent without build feedback needed: (a) the failing path in the original log is `ext/xxHash/...`, but `Build.PL` with `c_source => ['.', 'src']` is a recursive glob (the flags `-I. -Isrc -Iext/xxHash` in the compile line are the visible hint). (b) The source package format is `3.0 (quilt)` (`debian/source/format`, `debian/patches/` exists); an agent must know that any edit to an upstream file creates a pristine copy under `.pc/<patch>/` in the unpacked package, so "edit the offending C file" cannot work when the build globs the whole tree. (c) `grep -rn x86dispatch` shows it is unused by `xs/`, so it can be excluded. (d) An edit only in `debian/rules` or `Build.PL` is not affected (a `.pc/` backup of `Build.PL` exists but is not a `.c` file). A check that would have led there: "for an edit to file F, find who enumerates F (grep Build.PL/Makefile/CMakeLists for globs) and test whether `.pc/**/F` would match".
   Specific to this package or general? The `.pc/` copy only matters when (1) the build enumerates sources recursively from the package root and (2) the agent edits a file of the globbed type. Here that means Module::Build with `c_source => '.'` (or any `find . -name '*.c'`, `$(wildcard **/*.c)`, `file(GLOB_RECURSE ... ${CMAKE_SOURCE_DIR})`, setuptools `glob('**/*.c')`). Most packages list sources explicitly or glob `src/`, so it is not generic, but it will recur for such globbing builds. Not tested on other packages (inference).

## 4. r-cran-randomfieldsutils, jammy (`launchpad-jammy-amd64-arm64-r-cran-randomfieldsutils-ff260e110374`)

1. reproduces today: yes, ubuntu:22.04 `--platform linux/arm64` (checked `uname -m` = aarch64), R 4.1.2; same load error.
2. root cause: the package decides at load time which x86 SIMD features exist using `cpuid`. `configure.ac:95-110` tries to compile a `cpuid` inline-asm snippet; on arm64 that fails (log: `checking whether cpuid works under asm... no`), so `-DLINUXCPUID` is not set and `src/zzz_RandomFieldsUtils.h:253-259` (`#else` branch of `AVAILABLE_SIMD`) defines `Available()` as `ERR("SIMD checks are not available on your system ... Use 'SERVER' on Linux systems and alike.")`. The first call is `loadoptions()` in `src/xport_import.cc:140-141`: `if (!sse) RFERROR(...)` and `sse` is `Available(1,EDX,25)`. That error aborts `R CMD INSTALL`'s "testing if installed package can be loaded" step (original log lines 1906-1912). `debian/rules` already passes `-DREQUIRED_SIMD=0` (this only affects the consistency asserts, not `Available()`), so no configure flag can avoid the call.
3. what our agent's edit did: rc5 added `-DLINUXCPUID` to `--configure-args` in `debian/rules`. The rc5 compile lines (log 2070) show the flag never reached the compiler (the comment in debian/rules already notes `--configure-args` is ignored; only the `sed` on `configure` takes effect), and with the flag the cpuid asm would not assemble on arm64 anyway. Result: identical error. rc9c changed `src/zzz_RandomFieldsUtils.h` to `return true;` (without ERR) for the stub. That makes `sse` pass, but also reports AVX2/AVX512 etc. as available on arm64; not built by us. Inference: the `avx2`-guarded branches in `utils.cc` would then run x86 kernels that are not compiled in.
4. fix: report all x86 features absent and skip the x86-only baseline check. Two small source edits (header copy in `inst/include/` is identical to `src/`; I edited both to keep them in sync, the build only needs `src/`):

+      /* no cpuid on this platform (e.g. arm64): report every x86 SIMD feature as absent */ \

 #endif

   verified: PASS, ubuntu:22.04 arm64, `dpkg-buildpackage -b` rc=0 ("DONE (RandomFieldsUtils)"). Extra check: `library(RandomFieldsUtils)` loads and `solve(A,b)` returns a residual of 1.4e-13 and `all.equal` to base `solve`. The package has no tests in the tree, so no test was weakened. 5. what an agent without build feedback needed: (a) the failing message is a run-time error text, so grep the source for it: `grep -rn "SIMD checks are not available"` leads to the `AVAILABLE_SIMD` `#else` branch within a minute. So there is no flag that can turn this on for arm64: the fix must change what `Available()` does. (c) Then grep the callers of `Available`/`sse`/`avx2` (`xport_import.cc:140`, `RFoptions.cc:525-528`): the `sse` baseline check at load must be dropped on non-x86 and everything else must answer false, otherwise AVX code paths are selected. (d) The debian/rules comment itself says the configure-args route does not work; an agent should distrust adding flags there without a way to confirm they reach the compiler (the compile line in the original log shows exactly which `-D` flags are passed). A check that would have led there: compare the `-D` flags on the original compile line with the flags the edit intended to add.
6. class: x86-only code.
