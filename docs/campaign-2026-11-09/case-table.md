## 1. rcran (r-cran-digest 0.6.32-1, mantic, amd64->arm64; launchpad-mantic-amd64-arm64-r-cran-digest-7a42effc961f)

- **Validator outcome:** PASS, 96 s, one edit, 10 turns, 127k tokens (6 of the turns were wasted re-verification).
- **True root cause (PROVED):** the vendored, hand-written `src/crc32c/crc32c_config.h` hard-codes `#define HAVE_MM_PREFETCH 1` (line 15). `crc32c_prefetch.h:13-18` does `#if HAVE_MM_PREFETCH` then `#include <xmmintrin.h>`, an x86-only header. First error: Log 1995 `crc32c/crc32c_prefetch.h:18:10: fatal error: xmmintrin.h`. HAVE_BUILTIN_PREFETCH is already 1, so the x86 branch is never needed. blake3 is already guarded (IS_X86 at blake3_impl.h:39-53). Votes: not refuted.
- **Maintainer fix:** DEP-3 quilt patch `crc32c-arch-prefetch.patch`; in crc32c_config.h replace `#define HAVE_MM_PREFETCH 1` with `#if defined(__x86_64__) || defined(__i386__) || defined(_M_X64) || defined(_M_IX86)` / `#define HAVE_MM_PREFETCH 1` / `#else` / `#define HAVE_MM_PREFETCH 0` / `#endif`.
- **Our repair maintainer-quality?** Yes (the agent wrote the same arch guard).
- **Decisive evidence:** Log 1994-1996 plus `source/src/crc32c/crc32c_prefetch.h:13-18` and `crc32c_config.h:15`. All available without a build. dep has no xmmintrin.h for the target.
- **Class / frequency:** hard-coded or frozen x86 feature macro in a vendored/pre-generated config header gating an x86-only header. **Common.**
- **Status:** repaired cleanly. Waste: the "[fixed]" verdict was ignored for 6 turns, and the "8 constructs" wording invited an audit.

## 4. html-xml-utils (resolute, amd64->arm64; launchpad-resolute-amd64-arm64-html-xml-utils-fe68b3f14b84)

- **Validator outcome:** PASS (agent 0.3.2, 8 attempts, 40 turns, 328 s). The accepted edit disables LTO, optimisation and hardening flags (noopt, nolto, `CFLAGS=` on the make line).
- **True root cause (PROVED by reproduction):** a parallel-make race on the helper `cexport`. `Makefile.am:136-138` rule `.c.e` runs `$(MAKE) cexport` recursively. With `make -j8`, unent.e and dtd.e both trigger it. Log ~1326-1331 shows `make cexport` twice, two compiles to the same `-o cexport.o` (1332, 1335), two links (1376, 1378). First error Log 1377 `lto1: internal compiler error: resolution sub id ... not in object file`; then lto-wrapper fatal (1390-1393), cexport Error 1 (1394), `./cexport: No such file or directory` Error 127 (1399-1401), dh_auto_build exit 2 (1403). Experiment on native arm64 (ubuntu:26.04, gcc 15.2.0): the unmodified source failed 6 of 6 at -j8 with three symptoms (`Text file busy` x3, `cexport.o: file too short` x2, the organizer's lto1 ICE x1); -j1 passed (one run). It is NOT arm64-specific: it is timing and core count on the builder.
- **The validator also hits the race.** The baseline (comment-only edit) failed once at the validator's own `make -j2` with `./cexport: Text file busy` (Error 126). So "passes only because of -j2" is too strong. The -j2 failure rate is UNKNOWN (one baseline run).
- **Maintainer fix (verified):** in debian/rules add
  ```
  override_dh_auto_build:
  	dh_auto_build -- cexport
  	dh_auto_build
  ```
  Fix A passed the real validator (275.6 s; 82 `-flto=auto` lines remain, so LTO and hardening are kept) and 6 of 6 -j8 container builds. Fix B (`dh_auto_build --no-parallel`) also passed (285 s; 3 of 3 -j8). Fix A is preferred (serialises only the helper). Upstream-style alternative (UNTESTED): patch Makefile.am to depend on cexport instead of the recursive make, then autoreconf.
- **Our repair maintainer-quality?** NO. It masks the race by perturbing flags and does not fix it. Do not use as a template.
- **Decisive evidence:** duplicated `make cexport` and duplicated cexport.o compiles in the log (1326-1335, 1376-1378); `make -j8` ~1325; Makefile.am:134-138. Available without a build.
- **Class / frequency:** parallel-make race on a recursively-built helper; symptom is a compiler ICE or "file busy" in a helper link. **Occasional.** One case is not enough to promote the template to a general rule.
- **Status:** repaired by accident. Fix A verified by experiment.

## 5. ectrans (noble, amd64->arm64; launchpad-noble-amd64-arm64-ectrans-50e45e72102d)

It was fixed in 1.2.0-2/-3/-3build2 (targets name `/usr/lib/x86_64-linux-gnu/fortran/gfortran-mod-15/fiat`, .mod files shipped there). No arm64 build of the fixed fiat exists on Launchpad (arm64 only has 1.2.0-1 and 1.0.0-4), so this is **per-architecture packaging lag**. INFERRED: the amd64 ectrans build used 1.2.0-3 (consistent with timestamps; its log was not fetched). Correction to the vote: line numbers in dep are 8268 (header), cmake files at 8348-8352; rules: FMODDIR at 14, `-I$(FMODDIR)` at 18, configure target at 39/40.
- **Maintainer fix:** the proper fix is in fiat-ecmwf. That cannot be applied here: manifest forbids anything outside `input/**` and the dependency set is frozen. In-package fixes (all PASS the real validator):
  - **Variant A (preferred, 441 s):** a CMake loop after `ecbuild_find_package(NAME fiat REQUIRED)` (top-level CMakeLists.txt ~line 19) that, for each non-existent INTERFACE_INCLUDE_DIRECTORIES dir, redirects to `file(GLOB /usr/include/${triplet}/fortran/gfortran-mod-*/${leaf})` only, dropping dirs with no match. No `/usr/lib` glob, no system writes.

  - **Failed:** B1 (symlinks to `$(FMODDIR)`: it resolves to the EMPTY `/usr/lib/.../gfortran-mod-15` on arm64, so the symlinks dangle); C2 (missing `usr/bin` in the fake prefix). Appending `-I` flags in rules cannot work because the failure is CMake's generate-time check.
- **Our repair maintainer-quality?** NO. It is a validated workaround in ectrans for a defect in a dependency; it is also broader than variant A (it globs `/usr/lib` too).
- **Decisive evidence:** Log 2191-2196 versus dep 8284-8343 (the hosted agent does not see dep as designed; the glob substitutes for it), `source/src/trans/CMakeLists.txt:67,74`.
- **Class / frequency:** a dependency's installed `*-targets.cmake` names a path the package does not ship (per-arch packaging lag). Rule for the agent: repoint (CMake) or provide (symlink) the real dir the .deb file list shows; do not trust `$(FMODDIR)`. **Occasional**; the critic's sample showed zero other instances.
