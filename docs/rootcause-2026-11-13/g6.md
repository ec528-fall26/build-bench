# g6 root-cause report: 19 amd64-target cases (13 Nov 2026)

Method. Every case: original log (`logs/target-failure.log`) read against the rc.5 log and the unpacked source. Emulated amd64 builds (2): libotr (reproduction + fix verified) and kissat (reproduction + no-LTO startup check). One native arm64 probe for zim-tools. No rc9c repair.diff exists for any g6 case (searched rc8, rc9, rc9b, rc9c, rc9d), so "what our edit did" is inferred from how the rc.5 log differs from the original. Inferences are marked (inf). "not built" = analysis only.

## 0. The validator runs amd64 under QEMU user-mode on an arm64 host (matters for every case)
Evidence in the rc.5 logs: backend `deb-obs-build`, `BUILD_ARCH=x86_64:i686:...`, a `[Build-Bench] ... isolated-chroot is privileged` note, lines `qemu: uncaught target signal 11 (Segmentation fault) - core dumped` (libengine-gost-openssl, zim-tools, kissat) and `signal 6` (dqlite, 218 times), uname-style output `machine = "x86_64"`, release `6.8.0-137-generic`, interface `eth0 172.17.0.5` (lua-luv; a docker container), ptrace `error #38: Function not implemented` (python-ptrace), Go `runtime: lfstack.push invalid packing node=0xed95...` (v2ray; guest pointers above 2^47, impossible on real amd64). My own container on this host also shows `/usr/bin/qemu-x86_64` as PID 1 for amd64 images.
The ORIGINAL logs are real amd64 hardware (Launchpad `lgw01/lcy02/bos03-amd64-NNN`, kernels 4.4 to 5.4), so original failures are not emulation artefacts; rc.5 failures often are.
Emulation costs seen: libotr full test run 1650 s vs 120 s native; pysam compile still running after 11 000 s; kernel features missing: ptrace, Linux AIO (dqlite), and wall-clock tests drift (pyinstrument 0.129 s vs 0.1 s +-20 %).

A. Test's own bug or race; a test edit addresses it (5): libotr (VERIFIED), python-pyinstrument, python-ptrace (original test_link only; emulation blocks the rest), alertmanager-irc-relay (race, edit unverified), lua-luv (racy thread test; no edit found, original SEGV is a flake).
B. Real defect in package code or flags (6): kissat (LTO-built binary crashes at startup; fix VERIFIED to start), ocaml (LTO flags leak into test C compiles; edit unverified), jellyfish (x86 inline asm hypothesis, or probabilistic test), zim-tools (std::regex recursion depth, inference), libengine-gost-openssl (provider SEGV, unpinned), python-pyppmd (decoder crash/hang, unpinned).
C. Packaging bug visible only in the arch:all build (1): python-pysam (then the 4 h limit under emulation).
D. Original builder environment/archive state or emulation, nothing sensible to edit (5): grub2-signed, cowsql, dqlite, golang-v2ray-core, pyfftw.
E. Toolchain drift, cause not pinned (1): sbsigntool.
F. Time limit (1): libcrcutil (original: hang in a benchmark loop; rc.5: 4 h; `--noperf` option unverified). ocaml and pysam and pyfftw also hit 4 h in rc.5.
Counts: A 5, B 6, C 1, D 5, E 1, F 1 = 19.
What an agent without build feedback could have fixed from log+source alone: libotr, pyinstrument, ptrace test_link, pysam packaging line, alertmanager race, kissat (only if told "binary crashes on --help => try -fno-lto"), ocaml (LTO warnings visible in the log), libcrcutil (--noperf, unverified). ## 1. alertmanager-irc-relay (groovy, go 1.14)
1. reproduces today: not built (groovy go-1.14 image, Go test hang of 10 min).
2. root cause: test race in `irc_test.go` `TestSendAlertDisconnected`. Original log: `=Server= Received JOIN #foo/#bar/#baz` then `=Server= No handler for command 'JOIN', skipping` (three times), then PINGs every minute and `panic: test timed out after 10m0s` with goroutine in `TestSendAlertDisconnected irc_test.go:484 (WaitGroup.Wait)`. The test installs `joinHandler` (which does `testStep.Done()` when it sees `#baz`) only AFTER `holdUserStep.Wait()` returns, but the server has already answered USER and the client's JOINs arrive before the handler exists, so `testStep.Wait()` never returns. Real amd64 hardware, so a timing race that the builder lost; not an arch defect.
3. our edit: unknown (no diff). rc.5 failed differently: 18+ tests `FAIL` in 0.01-0.08 s with `irc_test.go:266: Did not pre-join channels`: the server's `Log` lacks `QUIT :see ya` (server logs `Client ... disconnected` without `Received QUIT`) and the run ended with `FAIL ... 600.409s` (same 10 min timeout). Second race (QUIT read after `server.Log` is compared), made worse by emulation (inf).
4. fix (not built): remove the JOIN race:
```
--- a/irc_test.go
+++ b/irc_test.go
@@ func TestSendAlertDisconnected
-	var testStep, holdUserStep sync.WaitGroup
+	var testStep, holdUserStep, joinStep sync.WaitGroup
@@
 	server.SetHandler("USER", holdUser)
+
+	// Install the JOIN handler before the session can complete.
+	joinStep.Add(1)
+	server.SetHandler("JOIN", func(conn *bufio.ReadWriter, line *irc.Line) error {
+		if line.Args[0] == "#baz" {
+			joinStep.Done()
+		}
+		return nil
+	})
@@
-	testStep.Add(1)
-	joinHandler := func(conn *bufio.ReadWriter, line *irc.Line) error {
-		// #baz is configured as the last channel to pre-join
-		if line.Args[0] == "#baz" {
-			testStep.Done()
-		}
-		return nil
-	}
-	server.SetHandler("JOIN", joinHandler)
-
-	testStep.Wait()
+	joinStep.Wait()
```
   verified: not built. The QUIT race in rc.5 has no small fix I can justify; a wait for the server to see QUIT before `server.Stop()` in the tests' shared pattern would be needed.
5. build-blind needs: the timeout stack names `irc_test.go:484`; the log interleaving "JOIN ... No handler" shows the handler was missing when the JOIN arrived; reading lines 455-490 shows `SetHandler("JOIN")` after `holdUserStep.Wait()`. A hint "tests that hang = look for a WaitGroup whose Done is in a handler installed later than the event" leads there.
6. class: test failure (test race); env/emulation worsens it.

## 3. libotr 4.1.1-6 (plucky)  [REPRODUCED AND FIXED]
1. reproduces today: yes, in a `ubuntu:plucky --platform linux/amd64` container (emulated), Debian flags (`-O3 -flto=auto -D_FORTIFY_SOURCE=3`, gcc 14.2): `unit/test_auth` prints `ok 1`, then `qemu: uncaught target signal 11`.
2. root cause: test bug. `tests/unit/test_auth.c` `test_auth_clear()` declares `struct context ctx;` and calls `otrl_auth_clear(&ctx.auth)` on UNINITIALISED stack memory; `otrl_auth_clear` (src/auth.c:104) `free()`s `auth->encgx`, `gcry_cipher_close(auth->enc_c)`, etc. It only worked while the previous test (`test_auth_new`) left zeros in the same stack slot; with gcc 14 -O3 -flto the frames differ. Original log: `unit/test_auth (Wstat: 139 (Signal: SEGV)) Tests: 1 Failed: 0 ... planned 5 but ran 1` on real amd64.
3. our edit: nothing relevant: rc.5 still has the identical SEGV and also `regression/random-msg-disconnect-frag.sh Failed 13/1522` (random messages, not in the original; flaky/emulation (inf)).
4. fix (test's own wrong assumption, the precondition `otrl_auth_new` is what the old stack contents provided):
```
--- a/tests/unit/test_auth.c
+++ b/tests/unit/test_auth.c
@@ static void test_auth_clear(void)
 	struct context ctx;
 	OtrlAuthInfo *auth = &ctx.auth;
 
+	otrl_auth_new(&ctx);
 	/* API call. */
 	otrl_auth_clear(auth);
```
   verified: PASS for test_auth (all 5 ok, rc=0) in the emulated plucky container with the Debian flags. The rest of the suite was not run; the random-msg-disconnect-frag flakiness seen in rc.5 may still bite under emulation.
5. build-blind needs: the log names `unit/test_auth` SEGV after test 1 of 5. Reading `test_auth.c` shows test 2 uses a never-initialised local struct and `src/auth.c` shows `otrl_auth_clear` frees its members. Hint that leads there: "a SEGV after the first passing subtest in a TAP unit test: read the second subtest for uninitialised locals".
6. class: test failure with a real cause in the test.

## 5. python-pyinstrument 5.1.1+ds-1 (resolute)

-    while time.time() < start + 1 and counter_1.count == 0 and counter_2.count == 0:

@@ -117 +117 @@

## 10. kissat 4.0.2 (plucky)  [REPRODUCED, FIX VERIFIED TO START]
1. reproduces today: yes (emulated ubuntu:plucky amd64, Debian flags from dpkg-buildflags with `optimize=+lto`, `./configure -g`, gcc 14.2.0): EVERY invocation of the built `build/kissat` crashes at startup: `--banner`, `--version`, `--id`, `--compiler`, `--build`, `--help`, `-h`, and a trivial CNF all give `qemu: uncaught target signal 11`; so it dies in `main()`/`kissat_init` before argument handling. Matches the original: `help2man ... build/kissat` -> `can't get --help info` -> `Error 139` in `execute_after_dh_auto_build`, on real amd64, and rc.5's `kissat --banner exit status 139` (22 tissat failures).
2. root cause: link-time optimisation. Same source, same flags except `optimize=-lto` (no `-flto=auto -ffat-lto-objects`): `./kissat --banner` prints the banner and exits 0 (emulated plucky amd64, build in ~12 min). So the LTO-built binary segfaults at startup (gcc 14.2.0 -O3 -flto=auto; the precise miscompiled/UB site is not identified; inf: UB in kissat startup code that LTO exposes). `debian/rules` line 4 explicitly requests it: `export DEB_BUILD_MAINT_OPTIONS = hardening=+all optimize=+lto`. Why arm64 survives is not established.
3. our edit (inf from rc.5): the help2man step no longer fails in rc.5 (the build reached `dh_auto_test`), so the edit probably removed or neutralised the help2man call or its failure, which only moved the identical crash to the test step (`tissat: child terminated by signal 11 (SIGSEGV) ... kissat --banner`). It did not touch the LTO setting.
4. fix (VERIFIED for `kissat --banner` only; the tissat test suite was not run; scope it to amd64 if desired):
```
--- a/debian/rules
+++ b/debian/rules
-export DEB_BUILD_MAINT_OPTIONS = hardening=+all optimize=+lto
+export DEB_BUILD_MAINT_OPTIONS = hardening=+all optimize=-lto
```
   verified: banner works (rc=0) in the emulated plucky container; full `dpkg-buildpackage` and `make test` not run. Possible residual risk: tests may time out under emulation.
5. what an agent without build feedback needed: the original log shows `help2man: can't get --help info from build/kissat` and `Error 139` right after the link line `gcc -Wl,... -flto=auto -ffat-lto-objects ... -o kissat main.o ...`; i.e. the freshly linked binary segfaults without running a SAT problem. `debian/rules` line 4 says `optimize=+lto` explicitly. The check that leads there: "binary crashes on --help => remove LTO/-O3 first". An agent that instead removes the help2man call (as ours apparently did) just moves the crash into the tests.
6. class: compiler/toolchain version drift (LTO).
