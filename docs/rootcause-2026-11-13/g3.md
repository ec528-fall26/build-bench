# g3 root-cause report (13 Nov 2026). Host: Neoverse-V1 arm64 (SVE, i8mm), docker --platform linux/arm64, today's archive.

## xsimd 14.0.0-2ubuntu1 (resolute)
1. reproduces today: yes, resolute arm64, identical to the log (343 cases, 333 pass, 10 fail; 49 assertions).
2. root cause: strict-aliasing violation in the NEON bool load/store, exposed by GCC 15 at -O2 (the test build uses -mcpu=native, so the dispatched arch is i8mm+neon64 on this CPU; plain neon64 fails identically). include/xsimd/arch/xsimd_neon.hpp: `store(batch_bool<T,A>, bool*, neon)` for 4-byte and 8-byte T writes the lane with `vst1_lane_u32((uint32_t*)mem, ...)` / `vst1_lane_u16((uint16_t*)mem, ...)` into a `bool` buffer, and `load_unaligned(bool const*, ..., neon)` for 4-byte T reads `*(unsigned int*)mem`. GCC treats the store/load as uint32 access to a bool array and reorders or drops them. The generic `mask()`/`from_mask()` in common/xsimd_common_logical.hpp go through exactly this bool buffer, so `mask()` returns wrong values and `half && ihalf` counts are wrong (log: test_batch_bool.cpp:641 `CHECK_EQ(nb_false, s)` values (2, 4); :737 `all_false.mask()` values (2, 0); also compress/expand). Evidence: a 10-line program calling batch_bool<uint32_t>::from_mask(0xC).mask() prints 8 (neon64) / 1 (i8mm) at -O2, 12 (correct) at -O0 and at -O2 -fno-strict-aliasing. Debian's own patch fix_arm64_PR1241 already disables a sibling case (store of batch_bool<double>) with the comment "reproduce the issue and understand why it fails" (upstream issue 1232): same bug family.
3. what our agent's edit did: rc.5: no change submitted (Invalid worktree). rc9c repair.diff: rewrote popcount to __builtin_popcountll and changed common logical_and/logical_or to return batch_bool via `&`/`|`. Does not touch the load/store pun, so it would not fix it (inference from the root cause above; not built).

## libapache2-mod-auth-openidc 2.4.15.7-1 (oracular)
1. reproduces today: yes, oracular arm64 (old-releases), same assertion.
2. root cause: libcjose 0.6.2.3 rejects `"alg":"RSA1_5"` JWEs at import. Log line: `test_plaintext_decrypt: error in cjose_jwe_import: result "0" != expected "1" invalid argument [file: jwe.c, function: cjose_jwe_import, line: 1901]`. test/test.c:778 (`test_plaintext_decrypt`, and likely `_decrypt2` at :830) imports the RFC example JWE whose header is {"alg":"RSA1_5","enc":"A128CBC-HS256"}. I checked with a 10-line C program against the installed libcjose: the same compact JWE returns NULL with line 1901 for alg RSA1_5, while a header with RSA-OAEP imports fine. Nothing in this is architecture specific (inference: amd64 passed in the dataset because it was built at a different archive state, with a libcjose that still accepted RSA1_5; I did not verify amd64, and I did not find the cjose source to see which cjose change did this). Today's oracular has libssl 3.3.1; the log (build date 2024-05-29) had 3.0.13 and libcjose 0.6.2.3-1; so the failure is not explained by the OpenSSL drift alone.
3. agent's edit: rc.5: no change (Invalid worktree). rc9c: adds `-latomic` to LDFLAGS on arm64 in debian/rules: unrelated, would not change the failure.
4. fix: none found that obeys the rules. The only edits that make the test pass are replacing the RSA1_5 test vectors with RSA-OAEP ones (a test change that is not architecture-specific) or skipping those two tests. verified: not built (no candidate).
5. what an agent needed: the test name and the `jwe.c line 1901 invalid argument` line say the library rejected the input, not that the arm64 code is wrong. Hint that would help: "a test fails in a dependency call with 'invalid argument' on a standard RFC vector: compare dependency version in the log with the version on the other architecture; the case may be unfixable under the rules."
6. class: dependency API drift (library behaviour change), not arch specific.

## mlmmj 1.5.0-1 (questing)
1. reproduces today: yes (questing arm64): `mlmmj-receive:basics` hangs; same symptom as the log.
2. root cause: `char ch = fgetc(f); if (ch == EOF)` in src/gethdrline.c:39/66-67. On arm64 `char` is unsigned, so EOF (-1) becomes 255 and never equals EOF; the code `ungetc(255)`s it, the next getline returns the one-byte line "\377", forever. strace of `mlmmj-receive -L ml -F < mail` (which execs mlmmj-process) shows an endless `read(7,"",4096)=0` / `write(5,"\377",1)` loop. That is the four 300-second timeouts (basics, ctrl_faq, discard, addr_in_to_cc: log "Test case body timed out [300s]"). The 22 other `mlmmj-receive:*` failures "incorrect exit status: 1, expected: 0" come right after, and tests/fakesmtpd.c binds the fixed port 127.0.0.1:25678; the timed-out tests leave their daemonised fakesmtpd running (inference: this is why the later tests fail at once with no stderr; consistent with 31 stray fakesmtpd processes I found in my container after the hang).
3. agent's edit: rc.5: failed, 24 of 196 tests still fail as in the original (no rc9c diff for this case).

## hippomocks 5.0-2build1 (resolute)
1. reproduces today: yes (resolute arm64): `./test.exe` Illegal instruction (core dumped), `make test` Error 2.
2. root cause: HippoMocks' C-function mocking patches the target function with machine code, and its "ARM" branch (HippoMocks/hippomocks.h, class Replace, `#elif defined(SOME_ARM)` around line 293) writes 32-bit ARM instructions (`0xE59FF000` = `ldr pc,[pc]`, Thumb words) and a 32-bit pointer. SOME_ARM is also defined for `__aarch64__` (line 90), and line 106 enables `_HIPPOMOCKS__ENABLE_CFUNC_MOCKING_SUPPORT` for it, so test_cfuncs.cpp runs and executes garbage. gdb: SIGILL in `a()` at test_cfuncs.cpp:7, `_Z1av+4: .inst 0x61c657b0 ; undefined` (the replacement address written as an instruction). debian/control has Architecture: any, so arm64 builds it.
3. agent's edit: rc.5: failed, original failure persists (log truncated). No rc9c diff.
4. fix (verified PASS: full dpkg-buildpackage, resolute arm64, rc=0, all tests including the C-function ones run): add an AArch64 branch, `ldr x17,#8; br x17; <8-byte address>`, 16 bytes, which fits `backupData[16]`:

(the destructor's restore path already copies backupData back and clears the cache). The cheaper alternative, excluding aarch64 from `_HIPPOMOCKS__ENABLE_CFUNC_MOCKING_SUPPORT`, would also pass, because test_cfuncs.cpp is guarded by that macro, but it removes a feature from arm64 instead of fixing it; I did not build it. Source file: ~/rootcause/g3/hippo/hippo.diff.
5. what an agent needed: the log's last lines are only `./test.exe` / `Illegal instruction (core dumped)`; the actionable clue is in the source: hippomocks.h has per-arch machine-code patching (`SOME_X86`, `SOME_ARM`), with a comment saying the clear-cache is required, and the ARM constants are 0xE59FF000 (A32). An agent that greps the header for `aarch64` and sees it classified as SOME_ARM with A32 opcodes can derive either fix. Hint: "SIGILL in a test with no sanitizer output: look for runtime code patching or inline asm, and check which architecture variant each branch encodes".
6. class: arm-only code (32-bit ARM code path wrongly used on AArch64).

## libcvd 0.0~git20220106+ds1 (jammy)
1. reproduces today: yes (jammy arm64): original header, `tests/convolution.test` aborts (make Error 134 here; Error 139 segfault in the log; a heap overrun, so the symptom varies).
2. root cause: tests/convolution.cc calls `convolveGaussian(img, out, 1.0)` on a 2x5 float image. Sigma 1.0 gives ksize 3, window swin 6. On x86 the SSE implementation (cvd_src/SSE/convolve_gaussian.cc) is used; on other architectures configure.ac selects cvd_src/noarch/convolve_gaussian.cc, which calls the generic template in cvd/convolution.h (~line 495). That template assumes w > 2*ksize and h > 2*ksize: its "beginning of row" loop writes next_row[j] for j<ksize (w=2), `convolveMiddle(..., w - swin, ...)` gets -4, and the end loop starts at j = w - ksize = -1. So the test hits a latent bounds bug that only the non-SSE path has.
3. agent's edit: rc.5: failed, original failure persists (log truncated). No rc9c diff.
4. fix: in the template, handle images no larger than the window with a direct clamp-to-edge version (same border semantics as the streaming code). Verified PASS: full dpkg-buildpackage on jammy arm64, rc=0 (tests/convolution passes).
