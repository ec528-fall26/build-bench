**Conclusion.** Verified: the trigger is -Wl,-Bsymbolic-functions, which Ubuntu's dpkg-buildflags adds by default, combined with the aarch64 ifunc dispatch objects. This is a BFD 2.41.50.20231214 bug. Stripping that flag (rung A) passes the real validator. Switching to ld.gold (rung B) also passes. Dropping bindnow (C) and disabling LTO (D) do not help. I did not test -Wl,--no-relax, -Wl,-z,lazy, -fno-plt or disabling the ifunc dispatch. Edit A already passes, and those were optional. The wrapper trace used a real validator run, not a container reproduction. The reason is that the container's current binutils is not the pinned Dec-2023 2.41.50 build. The causal link between -Bsymbolic-functions and the assertion is inferred from A passing while C and D fail, plus the known ifunc/symbolic behaviour. I did not run a link-level bisect, and A was not compared against a bare -Bsymbolic-functions-only link. Maintainer acceptability is inference, not tested. A one-line DEB_LDFLAGS_MAINT_STRIP in debian/rules is a standard, accepted Debian idiom. The cost is that libmceliece.so.1 loses -Bsymbolic-functions on every architecture, so intra-library calls go through the PLT and can be interposed. That is a minor performance and symbol-binding change. A maintainer would likely prefer to scope it to arm64, for example wrapped in ifeq ($(DEB_HOST_ARCH),arm64), to keep amd64 output unchanged. I did not run that guarded variant. Rung B is less likely to be accepted, since gold is deprecated and must be a Build-Depends, though it is in the frozen dependency set here.

**Implication for the agent.** The agent can use this macro or rule for libmceliece and similar cases. If the aarch64 ld log shows 'BFD ... assertion fail ../../bfd/elfnn-aarch64.c:9754' for a shared link, edit debian/rules to add 'export DEB_LDFLAGS_MAINT_STRIP = -Wl,-Bsymbolic-functions'. A rule-matching template should fire on that exact assertion string, and the optional arm64 guard could be added as a refinement. Fallback: -fuse-ld=gold on arm64. Do not try -bindnow or LTO changes for this assertion, since both are ruled out here. Verified replay JSON for the minimal fix: ~/scratch-lm/rp/A.json. It edits input/debian/rules, replacing 'export DEB_LDFLAGS_MAINT_APPEND = -Wl,-z,noexecstack\n' with that same line followed by 'export DEB_LDFLAGS_MAINT_STRIP = -Wl,-Bsymbolic-functions\n'. The result passed the real validator in 298s.

Open: (1) Does the guarded variant (arm64 only) also pass? Expected yes, but not run. (2) Does the unguarded strip change the amd64 build or symbols file (libmceliece1.symbols.amd64)? Not tested. (3) Is the exact root cause the interaction of -Bsymbolic-functions with STT_GNU_IFUNC on aarch64 in this binutils? It is inferred, not bisected at link level. (4) Do the optional rungs (-z lazy, --no-relax, -fno-plt, dispatch disabling) also work? Not run and no longer needed. (5) Will the hosted validator's binutils match this noble snapshot? The log shows the same 2.41.50.20231214 version, so the fix should transfer.

**Implication for the agent.** Replace the 'not repairable, stop' verdict for this class (a Debian -dev package whose shared runtime library is missing, so the link falls back to a non-PIC static archive on amd64) with a repair rule: do not stop. **Conclusion.** Verified facts. **Implication for the agent.** Rule: when an arm64 build log shows a gcc ICE or odd failure in a helper binary (here lto1 ICE linking cexport) and the Makefile has a rule that recursively runs `$(MAKE) <helper>` from a pattern rule (.c.e: $(MAKE) cexport), diagnose it as a parallel-make race. Do not disable LTO or optimisation and do not strip flags. Tell the agent that an ICE in a link step with a duplicated compile or warning block in the log is a race signature. Verdict: the earlier accepted repair (noopt nolto, CFLAGS= on the make line) is dominated by Fix A and should not be used as a template. Keep Fix A as a candidate template for race-class failures.
