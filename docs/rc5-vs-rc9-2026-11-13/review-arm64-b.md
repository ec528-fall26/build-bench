# arm64-b: rc.9 vs rc.5 review (cases 13-23 of `passed_ids.py arm64`)

Judged by reading only. Items marked (inference) were not run.

| case | verdict | cause | rc5 edit | rc9 edit | why |
|---|---|---|---|---|---|
| libpdl-ccs-perl | DOUBTFUL | t/01_ufunc.t `andover` fails for missing=1,31,BAD: `got=(double) [0 1 1 1 1 1]  wanted=(double) [1 1 1 1 1 1]` (row 0 wrong). | ccsufunc.pd: `tmp_type` of the `or` and `and` accumulators `char` to `int`. | ccsufunc.pd: leaves `char`, adds `tmp_init => 'tmp = 1;'` to `and` only. | Real cause (inference): default init is `tmp = $nzvalsIn(NnzIn=>0)`; row 0 contains -2, and double -2.0 to plain `char` is 0 on arm64 (unsigned char, saturating convert) but -2 on x86, so `tmp && ...` stays 0. rc9 does not fix the conversion. It makes the first value of every group be ignored (loop starts at nnzii=1), so row 0 now gets 1 and the test data should pass. Remaining risks: the reset path `tmp = $nzvalsIn(nnzii)` still converts to char for later groups (no negative data in this test), the `or` accumulator is untouched, and the first element is now semantically skipped (wrong for a stored 0). Passes only if the failure was limited to row 0 and no other test (CCS/t/03_ufuncs.t, which did not run before the abort) uses negative first values. |

| golf | SOUND | `cc1: error: '-fcf-protection=full' is not supported for this target` (compiling chandle.c). | Makefile: removes hard-coded `-fcf-protection` from CFLAGS; debian/rules: `export DEB_BUILD_HARDENING=0`. | Makefile: same removal; vmakefile: same removal from `_CFLAGS`. | libsieve | LIKELY FAIL | `header-lex.l:25:10: fatal error: header.h: No such file or directory` (-j8; `updating header.h` is printed right after the failure). | src/sv_parser/Makefile.am: adds `header-lex.c: header.h`; header-lex.l includes `"./header.h"`. | debian/rules: `CPPFLAGS += -I$(CURDIR)/src/sv_parser`; header-lex.l includes `"../sv_parser/header.h"`. | The tarball already ships header.h, so this is not a search-path problem: it is a parallel-make race where bison/ylwrap is regenerating header.h (`header.y` rebuilt, then `updating header.h`) while header-lex.lo compiles. rc5 adds the missing dependency, which serialises it. rc9 only changes how the file is found; if header.h is momentarily absent or being rewritten, it fails the same way (it may pass by luck of timing, inference). |
| lua-struct | LIKELY FAIL | `lua5.1: teststruct.lua:234: assertion failed!` (test: `assert(not pcall(lib.unpack, 'bc0', '\255'))`). | struct.c: `size = (size_t)lua_tointeger(...)` with an explicit negative check raising an error. | struct.c: keeps `size = lua_tonumber(L, -1)` and changes the argcheck to `size >= 0 && size <= ld - pos`. **Tally.** Of the 11 cases, rc.9's edit is EQUIVALENT in 1 (ogamesim), SOUND in 3 (west-chamber, golf, asmixer), DOUBTFUL in 1 (libpdl-ccs-perl) and LIKELY FAIL in 6 (pam-tmpdir, debugedit, gir2pas, gvars3, libsieve, lua-struct). So I expect at most 5 of 11 to pass: 4 fairly confidently, and libpdl-ccs-perl is a probable pass that depends on the first value of group 0 being the negative one (the tie ordering of `qsorti`) and on no other test using negative leading values. The failures are mostly the same pattern: rc.9 patched the apparent symptom (path, flag, extra option, comment touch) rather than the cause, as in pam-tmpdir (second stale object), gir2pas (help2man already passes --help), libsieve (race, not path), lua-struct (always-true unsigned compare), or wrote an invalid debian/rules (gvars3). No rc.9 edit passes by skipping or weakening a test; the debugedit edit would have been a rule risk (disables ELF checking, which the tests exercise) but also fails on "No errors". rc.5's debugedit edit itself weakens `--check-elf-strict` on arm64 and is a RULE RISK in the ground truth; gir2pas rc5 skips manpage generation (using the checked-in page), which is not a test change. The controller-added flags (debugedit, lua-struct) did not look like they interfere with either build, and neither case turns on them. Verdicts marked (inference) were not confirmed by a build.
