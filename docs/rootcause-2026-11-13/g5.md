# g5 root-cause report (13 Nov 2026)

Method notes. Facts come from the original logs, the sources under `~/rootcause/g5/<pkg>/tree`, and builds in containers named `g5-*`. Where a build was arm64-native instead of amd64/QEMU, it is said so. Anything marked (inference) is not verified.

## Pattern: arm64 built arch-any only (-B), amd64 built everything (-b)
The Launchpad logs for amd64 say `Build Type: binary` and run `dpkg-buildpackage ... -b`, which calls `debian/rules binary` / `build` and so also builds Architecture: all packages. The arm64 logs are not in the case dirs, so "arm64 used -B / binary-arch" is an inference from the rules files, except for tmpreaper where I verified it (below).
- Shows the pattern (an architecture-independent step runs only under -b): python-reportlab (docs in `binary-indep`; reproduced natively on arm64 with -b), fmtlib (`override_dh_auto_build-indep` sphinx; reproduced natively on arm64 with -b), tmpreaper (the `build:` target is only used by -b; `dpkg-buildpackage -B` on amd64 PASSES, `-b` FAILS, same container), python-pyaudio (docs package is Architecture: all, so `dh_linktree` for it only runs under -b), pynfft (only its `build_sphinx` step is indep; its Cython failure is NOT indep, see case).
- Does NOT show it: cxref (binary-arch depends on install, which runs the docs, so arm64 also ran them; the difference is a per-architecture file, see case), python-cython-blis (x86-only kernels), dynarmic (x86-only backend file), globalplatform (rules enable tests per architecture), opentelemetry-cpp (rules ignore test failures on arm64 only).

Consequence for repair: for the indep cases the fix is a real port of the docs/packaging step to today's tools (Sphinx 7, Python 3.10 version strings, Cython 3), not a flag. An agent can see it from the log: `Build Type: binary`, the failing rule being in binary-indep / build-indep / override_*-indep, and `Architecture: any all` in the Launchpad control dump.

## cxref (oracular)
1. reproduces today: not run unmodified (the original log is the evidence). The fixed tree was built on ubuntu:24.10 amd64 under QEMU today.
2. root cause: `debian/rules` (`install-stamp`, the `$(MAKE) docs` line) runs `../src/cxref -O. -NREADME-TMP -xref README.c`. README.c includes `<math.h>`, and glibc on amd64 declares functions with `_Float128` (`/usr/include/x86_64-linux-gnu/bits/mathcalls-helper-functions.h:20: cxref: syntax error`, symbol `IDENTIFIER : _Float128`). cxref's parser does not know that type; on arm64 glibc does not use `_Float128` there. `debian/rules` copies `debian/cxref-cpp-supplement.defines.$(DEB_HOST_ARCH)` into the cxref-cpp defines, and only `.arm64` exists with that name. The amd64/i386/ppc64el files are named `cxref-cpp-supplemental.<arch>` (different name, so never copied) and they define `_DFloat128`, not `_Float128`. The patch `cxref-cpp-supplemental.defines` removed the older `-D_Float128='long double'` from doc/Makefile.
3. our edit: rc.5 failed "as originally" (`make[2]: *** [Makefile:104: readme] Error 1`). No rc9c diff for this case. I cannot see the rc.5 edit.
4. fix (new file, no test touched):
```
--- /dev/null
+++ b/debian/cxref-cpp-supplement.defines.amd64
@@ -0,0 +1 @@
+#define _Float128 long double
```
verified: PASS (`dpkg-buildpackage -b -us -uc -j2`, ubuntu:24.10 amd64 under QEMU, today's deps; no syntax error in the README step; cxref, cxref-doc and cxref-emacs debs built).
5. what an agent without build feedback needed: the failing line is cxref's own parser error naming `_Float128` in a glibc header. `debian/rules` shows the per-arch supplement mechanism (`cxref-cpp-supplement.defines.$(DEB_HOST_ARCH)`), `ls debian/` shows only the arm64 file matches that name while `cxref-cpp-supplemental.amd64` does not, and `debian/patches/c_warning_cleanups_and_defines_for_Float128` shows the historic `-D_Float128=...` fix. A check "for the per-arch file the rules reference, does one exist for the failing architecture, and does it define the symbol the error names" leads here. Renaming the existing `cxref-cpp-supplemental.amd64` alone would not be enough: it defines `_DFloat128`.
6. class: packaging step (per-architecture defines file missing or misnamed) plus a glibc header difference between architectures.

## tmpreaper (jammy)
1. reproduces today: yes, ubuntu:22.04 amd64 under QEMU. `dpkg-buildpackage -b` fails exactly as in the original; `-B` passes.
2. root cause: `debian/rules` lines 37-42: `build: build-stamp`, and `build-stamp:` runs `./tmpreaper -h | grep 'tmpreaper -- Version: '$(debian_version)-DEB`, but nothing builds `./tmpreaper` first (the real build is in `build-arch: dh build-arch`). Log: `You forgot to fix the VERSION in configure.ac! make: *** [debian/rules:42: build-stamp] Error 1`. `-B` calls `build-arch` only, so arm64 never reached `build`.
3. our edit: the rc.5 log shows the same failure (`debian/rules:43: build-stamp`), so no effective change.
4. fix:
```
--- debian/rules
+++ debian/rules
@@ -37,7 +37,7 @@
 build: build-stamp
-build-stamp:
+build-stamp: build-arch
 	dh_testdir
```
verified: PASS (`dpkg-buildpackage -b -us -uc -j2`, ubuntu:22.04 amd64 under QEMU; the version check prints `tmpreaper -- Version: 1.6.16-DEB`; the deb is built).
5. needed: the log shows the check runs before any compile step (no gcc lines between `debian/rules build` and the failure) and the `-b` command line; the rules file has a separate `build-arch:` target using dh. Hint: when the failing target is not one the arm64 flow uses, compare `build` against `build-arch`.
6. class: packaging step.

## python-reportlab (jammy)
1. reproduces today: yes, ubuntu:22.04 arm64 native with `dpkg-buildpackage -b` (identical traceback), so it is architecture-independent.
2. root cause: `debian/rules` line 8 `VER3 := $(shell python3 -c 'import sys; print(sys.version[:3])')` gives `3.1` on Python 3.10, so `$(wildcard $(CURDIR)/build/lib.*-*-$(VER3))` is empty (the build dir is `build/lib.linux-x86_64-3.10`). The log shows `PYTHONPATH= python3 genAll.py` then `ModuleNotFoundError: No module named 'reportlab'`. It runs in `binary-indep` -> `build-doc-stamp` only.
3. our edit: I have only the original log for this case in my listing (no rc.5 log was matched by the file search for it beyond the triage line "docs build cannot import reportlab"); no rc9c diff.
4. fix:
```
--- debian/rules
+++ debian/rules
@@ -5,7 +5,7 @@
 PY3VERS	:= $(shell py3versions -vs)
-VER3	:= $(shell /usr/bin/python3 -c 'import sys; print(sys.version[:3])')
+VER3	:= $(shell /usr/bin/python3 -c 'import sys; print("%d.%d" % sys.version_info[:2])')
```
verified: PASS (arm64 native jammy, `-b`; all debs including python-reportlab-doc built; not run on amd64, the change is architecture-independent).
5. needed: the log shows `PYTHONPATH=` empty, which comes from the `$(wildcard ...)` in the rule, and the Python version (`touch build3-python3.10`). The pattern to notice is `sys.version[:3]` on a two-digit minor version.
6. class: packaging step (Python 3.10 version-string bug in an indep-only target).

## pynfft (noble)
1. reproduces today: yes, on arm64 native noble `-b` (same `'cnfft3.pxd' not found`). So it is NOT amd64-specific today. (inference: the arm64 success reported for this version was with an older Cython or earlier state; the arm64 log is not in the case dir.)
2. root cause: Cython 3.0.7 (noble) has no implicit relative cimport: `pynfft/nfft.pxd:18: from cnfft3 cimport nfft_plan` -> `'cnfft3.pxd' not found` (`pynfft/cnfft3.pxd` exists beside it). Second Cython-3 issue after that: `pynfft/nfft.pyx:41: Cannot assign type 'void (void) except *' to 'void (*)(void) noexcept'` for `Py_AtExit(_cleanup)`. Third: `debian/rules` `override_dh_auto_build-indep: python3 setup.py build_sphinx -b html` fails with `invalid command 'build_sphinx'` (removed in Sphinx 7); this one is indep-only.
3. our edit: the rc.5 log is an original-style failure; I have no rc.5 edit details and there is no rc9c diff.
4. fix:
```
pynfft/nfft.pxd, nfft.pyx, solver.pxd, solver.pyx, util.pyx:
-from cnfft3 cimport ...
+from .cnfft3 cimport ...
pynfft/nfft.pyx:
-cdef void _cleanup():
+cdef void _cleanup() noexcept:
debian/rules:
-	python3 setup.py build_sphinx -b html
+	sphinx-build -b html doc/source doc/build/html
```
verified: PASS (arm64 native noble, `dpkg-buildpackage -b`; 52 tests ran in the pybuild test step; python3-pynfft and python-pynfft-doc built). Not run on amd64. Diffs: `~/rootcause/g5/pynfft/fix.diff` and `fix-rules.diff`.
5. needed: the log gives the exact Cython file:line and Cython version (3.0.7), and the file listing shows `pynfft/cnfft3.pxd` exists, so the import style, not a missing file, is the problem. Cython-3 migration knowledge (explicit relative cimports, `noexcept` on callbacks) plus knowing `build_sphinx` was removed. Errors come one after another and the log shows only the first, so the agent must list all three from knowledge.
6. class: dependency API drift (Cython 3, Sphinx 7).

5. needed: the error text names the destination `_static` as a directory; the package list shows `libjs-jquery ... ## python-cython-blis (resolute)
1. reproduces today: yes at the flag level. On ubuntu:resolute amd64 with gcc 15.2.0, each knl compile command from `linux-x86_64.jsonl` fails (37/37). The full package was not built (hundreds of kernels under QEMU).
2. root cause: gcc 15 removed Xeon Phi support: `gcc: error: unrecognized command-line option '-mavx512pf'` (log line 1420, command at line 1440). The flags come from `blis/_src/make/linux-x86_64.jsonl`, chosen by `setup.py get_arch_name` (znver3 and skylake-avx512 supported -> `x86_64`). 37 lines in that file mention knl: 4 optimized kernels (`-mavx512f -mavx512pf -mfpmath=sse -march=knl`) and 33 reference kernels (`-march=knl -mno-avx512f -mno-avx512pf -mno-avx512er -mno-avx512cd ...`). Tested on gcc 15: `-mavx512pf`, `-mavx512er`, `-mno-avx512pf`, `-mno-avx512er`, `-march=knl`, `-march=knm` are all rejected; `-mavx512cd`, `-mno-avx512cd`, `-mno-avx512f`, `-march=skylake-avx512` are accepted. The same 37 lines are in 5 jsonl files (linux-x86_64, linux-x86_64_no_zen3, darwin-x86_64, darwin-x86_64_no_zen3, windows-x86_64) and `blis/_src/config/knl/make_defs.mk` has the flags at lines 78, 84, 102, 108.
3. our edit: the rc.5 log shows the original gcc error. rc9c repair.diff removes only `-mavx512pf` from the 4 optimized-kernel lines in the jsonl files (some added lines in the diff show a malformed `"-mavx512f, "` string). Tested effect: with only `-mavx512pf` removed, all 37 knl commands still fail (4 on `cc1: error: bad value 'knl' for '-march=' switch`, 33 on `-mno-avx512pf`).
4. fix: in `blis/_src/make/linux-x86_64.jsonl` (the file used on amd64 Linux; for consistency also the other four jsonl files and `config/knl/make_defs.mk`), for the knl lines:
```
optimized (4 lines):  drop "-mavx512pf" and "-march=knl"   (keeps -mavx512f -mfpmath=sse)
reference (33 lines): replace "-march=knl","-mno-avx512f","-mno-avx512pf","-mno-avx512er","-mno-avx512cd" by "-march=haswell"
```
verified: PARTIAL. All 37 rewritten commands compile on gcc 15.2 amd64 (script `~/rootcause/g5/python-cython-blis/flagtest.py`: "fixed compiled 37 failed 0"). The whole build and runtime behaviour were not verified. (inference: the inline-asm knl kernels only run on KNL CPUs; `-march=haswell` keeps AVX2 for the reference kernels, as the original comment "We use AVX2 for reference kernels" intends.)
5. needed: the log gives gcc's exact option. `grep -rn avx512pf` over the tree lists the 5 jsonl files and make_defs.mk, and counting matches (37 per jsonl) shows two flag shapes. The key fact is that GCC 15 dropped KNL/KNM entirely (not only the `pf` flag). A check "run the edited gcc command" (e.g. `gcc <flags> -E -xc /dev/null`) catches the incomplete rc9c edit. JSONL edits must keep valid JSON.
6. class: compiler/toolchain version drift (x86-only code, absent from the arm64 build).
